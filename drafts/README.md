# 초안 폴더

블로그·칼럼·안내문처럼 **밖으로 내보낼 글의 초안**을 모아 두는 곳이다.

Claude에게 **"초안 폴더 README대로 ○○ 주제로 블로그 글 써줘"**라고 요청하면 아래 10단계를 순서대로 하나씩 거친다. 단계를 건너뛰지 않고, 각 단계가 끝날 때마다 결과를 짧게 보고한 뒤 다음 단계로 넘어간다. 사용자 확인이 필요한 단계(표시 ✋)에서는 멈추고 묻는다.

## 전체 순서 한눈에 보기

| 단계 | 할 일 | 도구 | 결과물 |
| --- | --- | --- | --- |
| 1 | 자료 찾기 | 위키·업무 가이드 검색 | 근거 문서 목록 |
| 2 ✋ | 독자·분량 정하기 | 사용자 확인 | 독자, 분량, 분할 여부 |
| 3 | 초안 작성 | 위키 정본 + fluent-korean 기준 | `YYYY-MM-DD-주제.md` (상태: 초안) |
| 4 ✋ | 사용자 1차 검토 | VS Code 미리보기 | 보완 요청 반영 |
| 5 | 법률 검증 | `/blog-legal-review` | 판정, 오류 목록, 최종본 (상태: 검증중) |
| 6 | 문체 다듬기 1 | fluent-korean 기준 점검 | 문장 수정 + 사실 대조 |

| 10 | 위키 보관과 수집 | 위키 marketing 저장, raw 복사, `/ingest` | marketing 문서, 소스요약, 커밋 |

## 단계별 세부 사항

### 1. 자료 찾기

- 위키 `0. CIAT WIKI`에서 주제의 정본 문서(`wiki/topics/`), 검토 체크리스트(`wiki/practice/`), 원자료(`raw/`)를 찾는다.
- `C:\dev\ciat-guide\고객가이드`에 같은 주제의 고객용 가이드가 있으면 함께 본다.
- 법령은 `law-kr`로 현행 조문을 조회해 둔다.
- 위키에 `[원문 확인 필요]`·`[강사견해]`로 표시된 내용은 따로 적어 두고, 본문에서 단정하지 않는다.

### 2. 독자·분량 정하기 ✋

- 기본 독자는 일반 납세자다. 용어는 풀어 쓰되 실무 쟁점의 깊이는 유지한다. 전문성이 드러나야 수임료가 납득된다.
- 분량을 정한다. 네이버 블로그 기준으로 길면 2편 분할(기본편·실무편)을 미리 정해 둔다.

### 3. 초안 작성

- 파일명은 `YYYY-MM-DD-주제.md`(작성 시작일 기준)로 하고, 머리말 `상태: 초안`으로 시작한다.
- 기본 구성은 다음과 같다.
  1. 핵심 세 줄 요약
  2. 제도 취지 (왜 생겼나)
  3. 누구에게 해당하나 (해당하지 않는 경우 포함)
  4. 용어 풀이
  5. 요건 (표)
  6. 가상 사례
  7. 실무에서 결론이 갈리는 지점
  8. 지금 확인할 것
  9. 사무소 안내 문단 (담당 세무사 성명 자리는 넣지 않는다, 2026-10-20 사용자 결정)
  10. 관련 법령, 인용한 판례·심판례 목록
  11. 해시태그 20개 (아래 「해시태그 규칙」)
  12. 「내부용」 영역 (제목 후보, 게시 전 확인 목록, 미확인 사항)
- **해시태그 규칙** (2026-10-21 사용자 지시)
  - 관련 법령·판례 목록 바로 아래, 「내부용」 구분선(`---`) 위에 한 줄로 20개를 넣는다. 게시 범위에 포함된다.
  - 고정 태그 5개: `#씨앗세무회계 #경산세무사 #경산회계사 #대구세무사 #대구회계사`
  - 나머지 15개는 글 주제로 고른다: 핵심 제도·쟁점명, 독자가 실제로 검색할 말(세목+상황), 본문의 세부 쟁점 순으로.
  - 띄어쓰기 없이 쓰고, 같은 뜻의 태그를 겹치지 않는다.
  - 문체 단계(6·7)에서는 해시태그를 고치지 않는다.
- 사례는 **가상 사례**로 쓰고 "설명을 위한 가상 사례"라고 밝힌다. 실제 고객 사례는 넣지 않는다.
- 처음부터 fluent-korean 기준으로 쓴다(서술어로 끝맺기, 조사 생략 금지, 엠대시 금지, 비유 대신 일반 어휘). 기준 파일은 `0. CIAT WIKI\.claude\output-styles\fluent-korean.md`다.
- 상담 명칭과 비용은 요금 페이지(https://ciatpartners.com/pricing)와 맞춘다.
- 머리말(`---` 사이) 값에는 콜론(`:`)을 넣지 않는다. 넣어야 하면 값을 따옴표로 감싼다. 넣으면 미리보기 오류가 난다.

### 4. 사용자 1차 검토 ✋

- VS Code에서 파일을 열고 `Ctrl + K` 다음 `V`로 미리보기를 연다.
- 설명이 부족한 곳, 빠진 내용, 독자 수준을 알려 주면 반영한다.

### 5. 법률 검증 (`/blog-legal-review`)

- 검증자 다섯(법령, 판례·심판례, 세무실무, 반대논리·광고 규정, 편집)이 원고를 본다.
- 국세청 해석은 검증자가 열지 못하는 경우가 많다. "확인 불가"를 "없음"으로 판단하지 않는다. 메인이 스킬에 적힌 방법(문서 ID로 본문 조회)으로 직접 확인한다. 기억나는 회신이 있으면 사용자가 알려 준다.
- 결과로 판정(PASS/REVISE/HOLD), 오류 목록, 최종본을 받는다.
- 최종본은 같은 파일에 덮어쓰고 상태를 `검증중`으로 바꾼다.

### 6. 문체 다듬기 1: fluent-korean 기준 점검

- 다듬기 전에 현재 상태를 커밋한다(「진행 관리 규칙」 2). 이 커밋이 백업이다.
- 기준 파일을 읽고 어긋나는 문장만 고친다(비유 표현, 명사형 끝맺음, 같은 낱말 반복, 생략된 성분).
- 고친 뒤 백업본과 대조한다: 숫자, 조문, 사건·문서번호, 링크, 제목 개수가 같아야 한다.

### 7. 문체 다듬기 2: `/humanize-korean`

- 머리말과 「내부용」 영역을 뺀 본문만 윤문한다. 작업 폴더는 세션 임시 폴더를 쓴다(OneDrive에 `_workspace`를 만들지 않는다).
- 법적 단정 수위("~해석이 있습니다", "볼 수 없다", "~하는 것이 안전합니다", "~할 수 있습니다")와 표, 장·절 번호는 바꾸지 않도록 지시한다.
- 게이트가 경고를 내면 의미 보존 최종 점검(finalize)을 거친다.
- 반영 전에 다시 대조한다: 숫자, 조문, 사건·문서번호, 링크, 표 줄 수가 같아야 한다. 하나라도 다르면 반영하지 않는다.

### 8. 위키 역반영과 백업 ✋

- 5단계에서 원문으로 확인했거나 위키와 다르게 나온 사실을 위키 정본에 반영한다. 위키 `CLAUDE.md`의 직접 병합 규칙(정본 갱신, 충돌 표시, `index.md`·`log.md` 갱신)을 따른다.
- 위키를 고쳤으면 커밋 범위를 확인한 뒤 커밋하고 GitHub에 올린다(사용자 확인 후). 다른 날 작업이 섞여 있으면 날짜별로 나눠 커밋한다.

### 9. 게시와 기록 ✋

- 「내부용」 영역의 게시 전 확인 목록을 처리한다(미확인 원문, 링크 동작, 상담 안내와 요금 페이지 대조).
- 게시할 부분은 H1 제목부터 「인용한 판례·심판례」 목록과 그 아래 해시태그 줄까지다. 머리말과 「내부용」 영역은 올리지 않는다.
- 해시태그는 본문 끝에 둔 채로 네이버 편집기 하단 태그 입력란에도 넣는다.
- 네이버 블로그는 표가 깨지므로 편집기 표로 다시 만들거나 이미지로 넣는다.
- 게시 후 머리말에 `상태: 게시완료`, `게시일`, `게시URL`을 적고 아래 목록을 갱신한다.

### 10. 위키 보관과 수집

게시가 끝난 글을 위키에 두 갈래로 넣는다. 위키 `CLAUDE.md`의 business 레이어 규칙과 수집(Ingest) 규칙을 따른다.

1. **marketing 문서로 보관**: H1 제목부터 「인용한 판례·심판례」 목록까지(「내부용」 제외)를 `wiki/business/marketing/<주제>-블로그.md`로 저장한다.
   - 머리말은 위키 형식으로 바꾼다: `type: business`, `business_type: marketing`, `status: active`, `domain`, `tags`, `게시일`, `게시URL`.
   - 근거가 된 정본 topics 문서와 서로 `[[링크]]`를 건다. 정본에는 "이 내용으로 쓴 블로그 글" 한 줄만 추가하고, 블로그 본문을 정본에 다시 옮기지 않는다.
   - 파일명은 위키 전체에서 유일해야 한다. 만들기 전에 같은 이름이 있는지 검색한다.
2. **raw로 복사해 수집 대상에 넣기**: 같은 게시본을 `raw/개인 스터디/블로그 원고/YYYY-MM-DD-주제.md`로 복사한다. raw는 이후 고치지 않는다(불변).
   - 파일명에 `#`, `^`를 넣지 않고 `[`로 시작하지 않는다.
3. **`/ingest`**: 위키 폴더를 열어 수집을 돌린다. 소스요약(`wiki/sources/`)을 만들되, 정본에는 8단계에서 반영하지 않은 새 사실만 넣는다.
   - 블로그 글은 정본에서 나온 파생물이므로 같은 내용을 정본에 중복으로 쓰지 않는다. 소스요약에는 "8단계에서 정본에 반영함"을 적고 marketing 문서와 정본을 링크한다.
   - 글에 실제 고객·지인 사례가 있으면 식별정보를 다시 확인한다(위키 「정보보호 · 사례 익명화」).
4. `index.md`·`log.md`를 갱신하고, 커밋 범위를 확인한 뒤 커밋하고 GitHub에 올린다(사용자 확인 후).

## 진행 관리 규칙 (2026-11-03)

진행 상황의 정본은 **각 원고 머리말**이다. 이 README의 표는 머리말에서 옮겨 적은 목록일 뿐이다.

1. **머리말 필드**: 단계가 끝날 때마다 `상태`, `거친단계`(예: `"1,3,5,6,7"`), `다음단계`, 필요하면 `제출원고판정`·`최종원고판정`, `위키커밋`(8단계 후)을 고친다. 값에 콜론이 있으면 따옴표로 감싼다.
2. **단계마다 Git 커밋**: 단계가 끝나면 `drafts/`만 커밋한다. 메시지는 `draft: <주제> N단계 <내용>` 형식이다(예: `draft: 중간예납 5단계 법률검증 최종본 PASS`). 5·6·7단계는 고치기 전 상태도 커밋해 두면 이력이 백업을 대신한다. 숫자·조문·사건번호·링크 대조는 `git diff`로 할 수 있다. 위키 정본을 고치는 8단계 커밋과는 섞지 않는다. 푸시는 사용자 확인 후에만 한다.
3. **별도 백업 파일은 필수가 아니다**: 위 커밋이 있으면 `6단계-백업.md`·`7단계-백업.md`를 만들지 않아도 된다. 윤문 기록처럼 이력에 남지 않는 산출물만 검증기록에 둔다.
4. **검증기록 폴더**: 글마다 `검증기록/<원고 파일명>/` 하나를 쓰고, 5단계 보고서는 `법률검증-보고서.md`, 제출본은 `제출원고.md`로 이름을 통일한다.
5. **게시 후 정리**: 10단계까지 끝난 원고는 `게시완료/`로 옮기고 이 표에서 상태만 남긴다. `drafts/` 바로 아래에는 진행 중인 글만 둔다. 검증기록 폴더는 옮기지 않는다.

## 상태 표시

`초안` → `검증중` → `게시완료` (또는 `보류`)

## 지킬 것

- 고객 이름·날짜·금액 등 식별정보를 넣지 않는다.
- 원문을 확인하지 못한 예규·수치는 본문에서 단정하지 않는다.
- 문체 단계(6·7)에서는 사실관계·법리·수치·사건번호를 바꾸지 않는다.

## 검색 유입과 상담 연결 점검 (2026-10-23)

초기 고객 확보의 우선순위는 **기장·신고 수임과 양도·상속·증여 상담**이다. 주제 선정·기존 글 개선·측정의 정본은 [홈페이지·블로그 검색성장 운영](<../wiki/business/marketing/홈페이지-블로그-검색성장-운영.md>)을 따른다. 아래 항목을 기존 1·3·9단계에 함께 적용하며, 검증·윤문 순서는 그대로 유지한다.

- **자료 찾기 때:** 독자의 검색 질문 하나와 그 질문을 이미 다룬 기존 글을 먼저 확인한다. 같은 질문이면 새 글보다 기존 글 보완을 우선 검토한다. 검색량·경쟁도를 확인하지 않았으면 추정 수치를 적지 않는다.
- **초안 때:** 제목 앞부분에 핵심 제도나 고객 상황을 두고 첫 문단에서 답과 적용 전제를 함께 밝힌다. AI 인용을 의식해 예외나 불확실성을 지우지 않는다.
- **근거와 기준일:** 조문·사건·회신 번호와 적용 시점을 식별할 수 있게 쓴다. 실제 검토 없이 날짜만 최신으로 고치지 않는다.
- **표와 이미지:** 핵심 요건·예외·숫자는 읽을 수 있는 본문 텍스트에도 남긴다. 네이버에서 표를 이미지로 바꾸더라도 핵심 답까지 이미지 안에만 두지 않는다.
- **관련 글:** 다음 질문에 답하는 기존 글 1~2개를 연결한다. 같은 키워드나 링크를 반복해서 채우지 않는다. 기존 해시태그 20개 규칙은 유지한다.
- **사무소 안내:** 기장·신고 글은 `/services/tax-compliance/`, 양도·상속·증여 글은 `/services/private-tax/`에 연결하고 비용은 `/pricing/`의 현행 안내를 확인한다. 새 상세 URL은 운영 배포 후 정상 응답을 확인하고 넣는다.
- **상담 명칭:** 단순 서비스·비용 문의, 기장 도입 상담, 개별 쟁점 본상담을 구분한다. ‘초기 상담 무료’처럼 현재 홈페이지의 유료 상담과 혼동되는 표현은 사용하지 않는다.
- **게시 후:** 게시일·URL과 변경 내용을 기록한다. 검색 노출·클릭·AI 인용·문의·수임을 구분하고, 고객별 정보는 위키 대신 승인된 업무시스템에서 관리한다.

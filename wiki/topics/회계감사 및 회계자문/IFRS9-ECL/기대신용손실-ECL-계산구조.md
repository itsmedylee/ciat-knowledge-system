# 기대신용손실(ECL) 계산구조

> **이 페이지가 ECL 지식의 정본 허브다.** 각 구성요소의 상세는 링크된 개별 정본 페이지가 소유한다. 여기서는 전체 공정과 요소 간 관계만 다룬다.
> 학습 순서는 [[IFRS9-ECL-완전학습가이드]], 실제 감사 수행 절차는 [[ECL-감사절차와-체크리스트]].

## 1. 먼저 결론

ECL은 **"이 금융자산이 앞으로 부도날 가능성과, 부도 시 실제로 잃을 금액을 현재 시점에서 미래지향적으로 추정한 금액"**이다.

가장 단순화한 골격:

```
ECL ≈ PD × LGD × EAD
```

그러나 **실제 IFRS 9 ECL은 이 곱셈이 아니라 하나의 공정(process)이다.** 숫자 세 개를 검증하는 것으로는 ECL을 검증할 수 없다 ([[IFRS9-ECL-02-심화-모형이해]]).

```
Exposure 존재
   ↓
신용위험 평가 (최초 인식 이후 얼마나 나빠졌는가)
   ↓
Stage 결정  ─────────────  [[ECL-스테이지와-SICR]]
   ↓
PD 결정 (12M or Lifetime) ─ [[ECL-PD-부도확률]]
   ↓
LGD 결정 (담보·회수·비용·할인) ─ [[ECL-LGD-부도시손실률]]
   ↓
EAD 결정 (한도성이면 CCF) ─ [[ECL-EAD와-CCF]]
   ↓
미래전망정보(FLI) 반영 ──── [[ECL-미래전망정보와-다중시나리오]]
   ↓
복수 시나리오 확률가중
   ↓
Model Validation ────────  [[ECL-모형검증과-오버레이]]
   ↓
필요 시 Overlay
   ↓
최종 IFRS 9 ECL
```

## 2. 왜 중요한가

금융회사 재무제표에서 **대손충당금은 단일 최대 회계추정**인 경우가 많다. 그리고 이 숫자는 계산식이 아니라 **판단의 누적**으로 만들어진다. 따라서 ECL 검토는 산술검증(Arithmetic Audit)이 아니라 **추정검증(Estimation Audit)**이다 ([[IFRS9-ECL-02-심화-모형이해]]).

```
ECL Excel:  100 × 10% × 40% = 4     ← 수학적으로 완벽
그러나 PD 10%가 틀렸다면? LGD 40%가 틀렸다면? Stage 자체가 틀렸다면?
→ 계산식은 맞고 재무제표는 틀릴 수 있다.
```

## 3. 기본 개념

### 3-1. EL과 UL

신용리스크 관리는 손실을 두 종류로 나눈다.

| 구분 | 의미 | 대비 수단 |
|---|---|---|
| **Expected Loss (EL)** | 평균적으로 예상되는 손실 | **충당금** |
| **Unexpected Loss (UL)** | 평균 범위를 초과하는 극단적 손실 | **자본(Capital)** |

`EL = EAD × PD × LGD`

**직관적 해석** — 100만원 대출, PD 10%, LGD 40%:
- 부도위험에 노출된 기대금액 = 100만원 × 10% = 10만원
- 부도나도 60%는 회수 → 실제 손실은 40%
- 10만원 × 40% = **4만원**

### 3-2. EL과 ECL은 뿌리가 같지만 같은 것이 아니다

| | EL (리스크관리) | ECL (IFRS 9) |
|---|---|---|
| 목적 | **위험에 충분히 대비** | **편향되지 않은 적정한 추정** |
| 보수성 | 보수적 마진이 정당화될 수 있음 | 과도한 보수성도 오류 |
| 구성요소 | PD·LGD·EAD | 동일하나 **회계목적 변환 필요** |

이 차이가 ECL 전체를 관통하는 원리다. **"충당금을 많이 쌓을수록 좋은 회계"가 아니다.** 원본 강의가 반복해서 강조하는 지점이며 `[강사 강조]`, Basel 숫자를 IFRS에 그대로 쓰면 안 되는 이유([[ECL-PD-부도확률]] 5-4, [[ECL-LGD-부도시손실률]] 5-5)와 Overlay 해제 논리([[ECL-모형검증과-오버레이]])가 모두 여기서 나온다.

### 3-3. 세 숫자의 역할

| 요소 | 질문 | 정본 |
|---|---|---|
| **PD** (Probability of Default) | 부도가 날까? | [[ECL-PD-부도확률]] |
| **LGD** (Loss Given Default) | 부도나면 얼마나 못 받을까? | [[ECL-LGD-부도시손실률]] |
| **EAD** (Exposure at Default) | 그때 얼마가 걸려 있을까? | [[ECL-EAD와-CCF]] |

## 4. 왜 IFRS 9 ECL이 등장했는가

과거 IAS 39는 **Incurred Loss Model**이었다 — "손상이 이미 발생했거나 객관적 증거가 나타난 뒤에 충당금을 잡는다."

금융위기에서 이 구조의 문제가 드러났다. 경제 악화 징후가 이미 있었는데도 손상사건이 명확해질 때까지 기다리다 보니 **충당금 인식이 너무 늦었다**(too little, too late).

IFRS 9는 이를 뒤집었다 — **손상이 발생할 때까지 기다리지 말고 앞으로 예상되는 신용손실을 먼저 반영한다.**

## 5. 판단 구조 — ECL을 "공장"으로 본다

[[IFRS9-ECL-02-심화-모형이해]]의 핵심 비유. 감사인은 완제품 숫자를 다시 계산하는 사람이 아니라 **각 공정에서 원재료가 올바르게 변환되었는지 보는 사람**이다.

| 단계 | 내용 |
|---|---|
| **원재료** | 대출잔액·한도·신용등급·연체정보·담보·부도이력·회수실적·거시경제자료 |
| **1차 가공** | 세그먼트 분류 → Default 정의 적용 → SICR 판단 → Stage 분류 |
| **2차 가공** | 12M PD / Lifetime PD / LGD / EAD·CCF |
| **3차 가공** | FLI → Scenario → Probability Weight |
| **사후 조정** | Overlay |
| **완제품** | IFRS 9 ECL |

### 5-1. ECL의 5개 층

하나라도 무너지면 최종 ECL을 신뢰할 수 없다.

| Layer | 질문 |
|---|---|
| 1. Classification | Stage가 맞는가? |
| 2. Data | 입력 데이터가 맞는가? |
| 3. Model | 모형이 맞는가? |
| 4. Assumption | 미래전망과 가정이 합리적인가? |
| 5. Governance | 검증·승인·변경관리가 되고 있는가? |

### 5-2. DATA → MODEL → JUDGMENT

[[IFRS9-ECL-03-Final-실전문제-감사실무]]가 제시하는 가장 압축적인 프레임. ECL 숫자 하나에는 항상 세 가지가 섞여 있고, **뒤로 갈수록 위험이 커진다.**

| 층 | 내용 | 예 |
|---|---|---|
| **DATA** | 실제 존재하는 정보 | 잔액·등급·연체·담보·회수 |
| **MODEL** | 데이터를 숫자로 바꾸는 방법 | PD·Lifetime PD·LGD·CCF·FLI Model |
| **JUDGMENT** | 사람이 결정하는 부분 | SICR·Scenario Probability·Model Selection·Overlay |

좋은 ECL 감사인은 계산을 잘하는 사람이 아니라 **어디까지가 데이터이고 어디부터가 판단인지 구분할 수 있는 사람**이다.

## 6. 사례 — 하나의 계좌를 끝까지

기업 A, 대출 100억원, 신용위험 악화로 Stage 2. `[교육용 가상수치]`

| 단계 | 값 |
|---|---|
| EAD (정액대출) | 100억원 |
| Lifetime PD | 12% |
| LGD | 30% |
| 단순 ECL | 100 × 12% × 30% = **3.6억원** |

FLI 적용 (시나리오별 ECL × 확률):

| 시나리오 | 확률 | ECL |
|---|---:|---:|
| Upside | 20% | 2.5억 |
| Base | 50% | 3.6억 |
| Downside | 30% | 7억 |

확률가중 ECL = 0.5 + 1.8 + 2.1 = **4.4억원**
모델 미포착 산업위험 Overlay +0.5억원 → **최종 4.9억원**

> 이 한 사례 안에 ECL 전 공정이 들어 있다. 같은 구조의 변형 문제가 [[IFRS9-ECL-03-Final-실전문제-감사실무]] 종합문제 1(최종 4.4억원)에도 있다.

## 8. 실무 체크포인트

- ECL 조서를 받으면 **PD 파일부터 열지 않는다.** 충당금 Bridge → Stage Distribution 순서로 본다 → [[ECL-감사절차와-체크리스트]]
- 감사 지도는 3축으로 압축된다: **A. Stage(핵심=SICR) / B. Risk Components(PD·LGD·EAD) / C. FLI(변수·시나리오·확률·Validation·Overlay)**
- 재무제표 표시·현금흐름표 연결: 대손충당금 설정·환입과 대손 제각은 **비현금거래**이므로 현금흐름표에서 복원해야 한다 → [[CF계정-대출채권]] (은행 CF 학습자료)

## 9. 핵심 정리

1. ECL은 공식이 아니라 공정이다. `PD × LGD × EAD`는 골격일 뿐이다.
2. 목적이 다르면 숫자도 달라야 한다 — 리스크관리(보수성) vs 회계(편향 없는 추정).
3. Stage 판단이 Horizon(12M ↔ Lifetime)을 결정하므로 충당금에 가장 큰 비선형 효과를 만든다.
4. 미래는 하나가 아니다 — 비선형성 때문에 확률가중이 필요하다.
5. 모델은 검증되어야 하고, 모델 밖 위험은 Overlay로 다루되 근거와 해제기준이 있어야 한다.
6. ECL 숫자를 볼 때는 항상 DATA / MODEL / JUDGMENT를 분리해서 본다.
